# db-agent 项目案例：从"调 API"到"能上线的 CLI 产品"

> 一句话：**这不是一个"让模型写 SQL"的项目，而是一个"让模型写 SQL 不出事"的工程系统。**
> 项目演进分 5 个阶段，每个阶段解决一类真实问题，共约 2.1 万行 Python、423 个测试（422 passed + 1 skipped）、47 条评测。

## 一、背景与问题

业务方查数有三痛：
1. **要背三套语法**——SQL / Hive / HBase 各是一套，非技术同事根本没法自助；
2. **改一个字段要等数据组排期**——报表需求排到几周后；
3. 市面上 Text-to-SQL 工具大多只做"生成 SQL"，**不负责执行、不负责权限、不负责改错**。

目标：做一个"说人话 → 查数 → 分析"的 Agent，而且**要把权限、可靠性、评测这些工程问题一起解决**，不是只调一个 LLM。

---

## 二、阶段一：单 Agent（先把"模型能干活"跑通）

**决策：手写 ReAct Loop，不用 LangChain AgentExecutor。**
原因：AgentExecutor 把决策循环封装成黑盒，无法精确控制 temperature、轮次上限、tool 结果截断、结构化错误返回。手写 ~250 行，每行都可控。

关键点：
- **工具真实执行**：模型只负责"决定调哪个工具"，执行结果来自真实 SQLite，回喂给模型——杜绝模型编造执行结果；
- **结构化错误**：SQL 写错返回 `{error, hint, retryable}`，让模型自己纠正，而不是 crash 整个循环；
- **成本控制**：prompt caching（system token 成本降到 ~1/200）、高频模板优先匹配（命中即零 LLM 调用）、结果双截断。

**产出：一个能稳定执行工具的 CLI Agent。**

---

## 三、阶段二：多 Agent 编排（从"一个大脑"到"一组分工"）

业务不止 SQL——还有 Hive 数仓、HBase KV、制度文档。一个 Agent 全包会混乱，于是用 **LangGraph** 显式建模：

- **对比过框架**：LangChain AgentExecutor（黑盒、多 Agent 出错定位不到步）、CrewAI（预置角色、自定义路由需绕框架）→ 选 LangGraph：Agent = 图节点、State 经 Reducer 合并、每步自动落 Checkpointer，**故障可定位、中断可恢复**；
- **10 节点 / 6 Agent**：Router → sql / strategy / hbase / hive / data_quality → analysis → reflection 自审；
- **Router 四层短路**：正则硬规则 → 上下文继承 → LRU 缓存 → LLM 兜底，约 80% 高频请求零 LLM 直接路由；
- **失败重规划**：Agent 超轮数带失败原因回 Router，跳过脏缓存，上限 1 次防死循环。

**产出：一个多引擎协同的编排系统。**

---

## 四、阶段三：权限与安全（Prompt 拦不住越权）

模型可能被诱导越权。经验：**软约束（prompt）不够，必须工具层硬拦截**：
- **5 角色 RBAC**：工具白名单 / 表白名单 / 行级 SQL 自动改写 `WHERE dept_id=X`；
- **三层正则护栏**：输入 / SQL / 输出，零 token 开销；
- **HITL 人工审批**：敏感列（salary/cost/budget）和 HBase 破坏性操作走 LangGraph 原生 `interrupt()` 暂停，等用户 y/n。

**产出：权限下沉到工具层，Agent 内部权限闭环。**

---

## 五、阶段四：可靠性闭环（从"能跑"到"挂了也不崩"）

Agent 落地最大的坑：**LLM 不稳定、会失败、会重复、会烧钱**。逐层解决：

| 机制 | 解决什么 |
|---|---|
| 指数退避重试 | 429/5xx/超时偶发 |
| SQL 错误回喂重写 | 模型写错表名/字段 |
| 失败重规划 | Agent 超轮数 |
| **熔断降级** | 连续失败达阈值 → 快速失败不烧 token，冷却后半开试探 |
| **工具幂等** | 写工具同参数 TTL 窗口内不重复执行（防重试重复副作用） |
| **告警** | 熔断打开 / Agent 超时 / 评测退化自动通知 |
| **checkpoint 续跑** | 会话中断可恢复 |
| **SSE 断流** | 客户端断线取消后台任务、心跳保活、前端自动重连 |

**产出：重试→自愈→熔断→幂等→告警的完整可靠性闭环。**

---

## 六、阶段五：工程化落地（从"demo"到"CLI 产品"）

1. **测试可信化**：LLM/Embedding 全 fake 化 → 423 个用例全离线、~10 秒、CI 绿——从"本地绿 CI 红"修成"真绿"；
2. **状态外置 Redis**：会话 + checkpoint 存 Redis 带 TTL，Redis 挂了自动回落 SQLite；
3. **向量库双后端**：Chroma / Milvus 可切换（`VECTOR_DB` 一行切换，Milvus Lite 嵌入式 → 集群 URI 指向生产）；
4. **CLI 产品化**：`db-agent` 命令、启动配置校验（缺 key 友好报错）、Docker 锁文件构建；
5. **评测体系**：47 条用例（13 条带 DB 实查事实断言）+ 护栏用例接 CI + Kimi 当 Judge 避免自评偏差；
6. **代码质量门禁**：ruff 0 error + pre-commit + pyright 收尾（223→156）+ orchestrator 拆分（1223 行 → 4 模块，API 不变）。

---

## 七、踩过的坑（工程经验的证明）

| 坑 | 怎么发现/解决 |
|---|---|
| 内置 `hash()` 跨进程随机化 → 样例库无限堆积 | 改用 `hashlib` 稳定 ID，upsert 真正去重 |
| Milvus URI 文件路径放环境变量 → 导入崩溃 | 本地路径只走构造参数，环境变量只放集群地址 |
| 拆分 orchestrator 后测试 monkeypatch 失效 | patch 改到代码实际所在模块 |
| `config["configurable"]["_X"]` pyright 报错 | 定义 `ConfigurablePayload` TypedDict + `agent_config()` |
| RedisSaver 只能在 DB 0 建索引 | checkpoint 用 DB 0 + 独立 key 前缀 |
| 样例库脏数据污染 few-shot | 加敏感列审计，含薪资/手机/账户等 SQL 不回流 |

## 九、反思与下一步

**做得对的：** 先把"模型能干活"跑通，再补工程化——每层都是被真实问题逼出来的，不是堆功能。

**没做的（诚实）：** Web 鉴权、pyright 归零、eval full 进 CI、限流、多实例压测——我的定位是单实例 demo，这些是上生产前的清单。

**一句话总结：** 这个项目的本质不是"写 SQL"，而是**驯服模型的不确定性**——用工具真实执行、权限硬拦截、自愈熔断、状态外置、评测兜底，把"模型 + Harness"从口号变成可交付的代码。

## 四、Harness 落地五个难点（根因 + 解法）

### 1. Agent 为什么越跑越偏（长链路）

**根因**：错误沿链路传播放大。4-5 个节点串行，每个节点的输出是下游的输入。10% 的偏差传到第 3 层变 50%，传到第 5 层变 80%。

**已有防御**：`_maybe_replan` 失败回 Router、Reflection 退回重写。

**缺的关键机制**：中间结果信号对齐。每步执行后检查输出是否跟用户 query 语义相关——不是 LLM 打分，是确定性规则。比如 SQL Agent 结果里没有 total 字段但用户问了销售额 → 信号不对齐，该触发重新分派。

### 2. Agent 自评为什么偏乐观

**根因**：LLM 有确认偏误（confirmation bias），同一个模型看不到自己输出里的问题。实际验证：Reflection 节点在生产中几乎全是 pass。

**正确做法**：你的 eval_runner 已经做对了——用 Kimi 独立评估，不用被测模型自评。但运行时 Reflection 仍用同一模型。

**改进方向**：快速路径保留 self-reflection（拦明显错误），高风险场景（涉及金额/对比）改用确定性规则检查——回答里有没有数字、有没有来源引用、是不是跟上一条一样（死循环）。

**规则不会偏乐观，LLM 会。**

### 3. Agent 总失败，工程师有什么用

**根因**：对工程师角色的理解偏差。工程师不是在"写代码让 Agent 成功"，而是在"设计系统让 Agent 失败的代价可控"。

**项目里靠确定性兜底的东西**（零 LLM 参与）：
- 硬规则 Router（9 条正则）——覆盖 ~80% 意图
- Router LRU 缓存——同样 query 零 LLM 调用
- 三层护栏——纯正则，零 token
- max_turns=10——防死循环
- TokenBudget + HybridWindowManager——防爆上下文

**这才是 Harness 工程的本质**：不是让 Agent 更强，是让它失败时不会炸。

### 4. 文档越长，Agent 越糊涂

**根因**：Lost in the Middle——LLM 对长文本中间的注意力显著低于开头和结尾。

**项目里的典型场景**：System Prompt + Tool Defs + 记忆注入 + few-shot + 模板提示塞一起 3000+ tokens，中间的约束很容易被忽略。

**改进**：关键约束放最前或最后；用 tool 替代 context——与其把 2000 字表结构塞 system prompt，不如让 Agent 主动调 describe_table。Tool 返回结果是"刚获取的"信息，LLM 对它的注意力远高于预先注入的文档。

### 5. Agent 代码越写越烂

**根因**：失败的工具调用历史留在 messages 里，后续轮次 LLM 看到之前的错误 SQL，倾向于"在上面改"而不是"从头想"。

**改进**：自愈重试时从 messages 里删掉失败的工具调用轮次，只保留摘要"上次尝试失败了，错误是 X，请重新开始"。原则：**历史是毒药，摘要才是解药。**

## 五、核心竞争力与薄弱环节

### 三个可以反复用的数字

| 数字 | 含义 | 使用场景 |
|------|------|---------|
| 94% | Eval 整体通过率（35 条） | 回答"质量怎么保证" |
| 39 commits / 12 天 | 从零到功能完整的速度 | 回答"开发效率" |
| 159 单测 + 36 Eval | 质量闭环规模 | 回答"测试怎么做的" |

### 核心竞争力

> "我不是什么都做了，而是知道每层为什么这样选，也知道哪里还不够。"

- **有体系**：Harness 六层框架，每一层能讲清楚"为什么这样做"
- **有自知**：知道哪些是 AI 帮你写的、哪些是自己设计的；知道哪里弱
- **有痕迹**：MISTAKES.md 记录踩坑过程，tracer.py 证明理解底层原理

### 诚实说话（面试时适用）

| 如果被问到 | 不要硬撑 | 说实话 |
|-----------|---------|--------|
| HBase/Hive 是真实的吗？ | "对接了集群" | "连接器抽象是真的，底层存储是模拟的。POC 阶段证明架构可行，生产换连接器" |
| 自愈是代码控制的吗？ | "有完整的自动恢复系统" | "prompt-driven 的协议 + 多层兜底。不是 100% 可靠，所以有重规划和 reflection 两道后手" |
| 为什么 commit 停在了 7.24？ | 编造理由 | "后面两周在跟 AI 深入打磨细节、补理论知识、准备面试。代码一直在改但忘了 commit——这是我的问题" |
| 用了 vibe coding 吗？ | "全部手写" | "核心架构是我设计的，但 AI 帮我加速了实现——7 月 22 日一天上线了 guardrails + entitlement + HITL，传统开发要几周。我知道每行代码在做什么，因为架构是我定的，code review 是我做的" |

### 最薄弱的 3 个环节

1. **用户输入层容错**：模糊查询、歧义反问、实体识别——"用户说了什么 → 系统怎么理解"这一步缺专门模块
2. **端到端行为测试**：159 单测覆盖模块，但没测"用户说 A，Agent 正确回答 B"的完整行为
3. **记忆衰减/去重**：向量库只增不减，长期运行检索质量会下降

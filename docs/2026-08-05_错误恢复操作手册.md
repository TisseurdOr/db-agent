# 错误恢复机制操作手册（s11 三层自愈）

> 2026-08-05 上线。对应 HARNESS.md 的 s11 Error Recovery。
> 设计背景：改动前 API 一次 429 就崩整轮对话、SQL 报错直接放弃、Agent 失败后垃圾结果流进 Analysis。

---

## 三层机制速查

| 层 | 触发条件 | 行为 | 上限 | 实现位置 |
|----|---------|------|------|---------|
| ① API 重试 | LLM 调用遇 429/500/502/503/529/连接超时 | 指数退避 + 抖动后重试 | 3 次（可配） | `utils/retry.py` |
| ② SQL 自愈 | `run_query` 返回 error | 错误信息回喂 → `describe_table` 核对 → 重写 SQL | 2 次（prompt 约束，`max_turns` 兜底） | `multi_agent/agents.py`（自愈协议）+ `tools/query.py`（`retryable` 标记） |
| ③ 失败重规划 | Agent 超 `max_turns` 失败（`is_agent_timeout`） | 失败结果移出 results，带反馈回 Router 重排 plan | 1 次 | `multi_agent/orchestrator.py`（`_maybe_replan`） |

**注意边界**：
- 400/401/403（参数错/key 错/无权限）**不重试**，立即抛出——重试没有意义。
- streaming 场景只在"还没输出任何内容"时重试，已有文字打到终端就直接抛错，避免重复输出。
- 重规划路径跳过 Router 硬规则和 LRU 缓存（两者都会复现失败的 plan），且补救 plan 不写缓存。
- 重规划额度用完后走原路径，由 Analysis 的超时警告兜底提示用户。

## 环境变量

```bash
LLM_MAX_RETRIES=3        # API 重试次数；测试想关掉重试就设 0
LLM_RETRY_BASE_DELAY=1.0 # 退避基数（秒）：第 n 次失败后等 base * 2^n + 抖动
```

覆盖：重试恢复/放弃/不可重试立即抛、自愈协议与错误载荷、重规划触发/跳过/额度耗尽、
图接线回归（每个 Agent 节点有回 Router 的边）、Task board 失败标记、trace 耗时非负。

### 现场演示（scripts/demo_recovery.py，三幕）

```bash
.venv/bin/python scripts/demo_recovery.py retry    # 第 1 幕：模拟 429，零 API 成本
.venv/bin/python scripts/demo_recovery.py heal     # 第 2 幕：SQL 自愈，需 API key
.venv/bin/python scripts/demo_recovery.py replan   # 第 3 幕：失败重规划，需 API key
.venv/bin/python scripts/demo_recovery.py          # 全部三幕
```

- 第 2/3 幕调真实 DeepSeek API（单幕 ≈ 2000-5000 tokens，费用可忽略）。
- 脚本自动设 `AGENT_USER=dba`（viewer 没有 run_query 权限，会被 Entitlement 拦截）。
- 第 3 幕用 monkeypatch 给 SQL Agent 注入一次假超时，checkpoint 写 `/tmp/`，不污染 `db/agent_state.db`。

### 日志观察点（判断机制是否触发）

| 日志标志 | 含义 |
|---------|------|
| `⚠️ LLM API 错误 (XXX)，1.5s 后重试 (1/3)` | ① API 重试触发，退避间隔应指数递增 |
| `run_query 报错 → describe_table → 重写 SQL` 工具链 | ② SQL 自愈在走协议 |
| `🔄 xxx Agent 失败，带反馈回 Router 重规划 (第1次)` | ③ 重规划触发 |
| `❌ Task failed: ...` + board 显示 `[✗]` | Agent 失败被任务板如实记录 |
| Router 第二次出的 task 描述比第一次更具体 | 重规划反馈起效的直接证据 |
| `📊 总计 51.7s · 5084t` | trace 汇总，耗时必须为正数 |

## 面试讲法（30 秒版）

"我的 harness 有三层自愈：**API 层**指数退避重试，只重试 429/5xx/超时这类可恢复错误；
**工具层**SQL 报错不放弃，错误信息回喂给模型，核对 schema 后重写，限 2 次；
**编排层**Agent 整体失败时不让垃圾结果污染下游，把失败反馈带回 Router 重新规划，限 1 次防死循环。
三层各有明确的重试预算，全部有零成本回归测试覆盖。演示脚本能现场复现每一层的触发过程。"

## 已知取舍

- 自愈重试预算写在 prompt 里而不是代码里——ReAct loop 本身就是重试回路，代码里只加了
  `retryable` 信号和 `max_turns` 硬兜底；如果模型不遵守 2 次限制，最多浪费几轮 token，不会死循环。
- 重规划上限 1 次：换一次思路足够，失败两次说明问题不在 plan，烧 token 重试没有意义。
- HITL interrupt（GraphInterrupt）不在任何重试范围内——那是暂停等人，不是错误。

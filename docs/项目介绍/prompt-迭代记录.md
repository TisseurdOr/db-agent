## 1. Analysis Agent：把"简洁"换成可衡量的硬约束

**提交**：`05059f0`
**文件**：`harness/orchestration/multi/agents.py: ANALYSIS_AGENT_PROMPT`

### 问题

Analysis Agent 是整条查询里占比最大的一段（约 50%），但输出一直压不下来。

原 prompt 只写了「回答要简洁」——**这是主观要求，模型不当回事**。实测照样写 600+ tokens。

### 改前

```
回答要简洁：先给结论和关键数字，再补简短依据。不要道歉开场，不要大段可视化字符。
```

### 改后

```
回答要简洁：先给结论和关键数字，再补简短依据。不要道歉开场，不要大段可视化字符。
如果数据不够支撑分析，说清楚缺什么，不要强行下结论。

【回答长度·硬约束】（为了控制生成长度与等待时间，必须遵守）
1. 第一行给**定论**（一句话，加粗），不做铺垫、不复述问题；
2. 正文最多 3 个要点，每个要点 1-2 句；
3. **正文总字数不超过 250 字**；需要列多项数据时用表格呈现，**表格不计入字数**；
4. 不要复述 SQL、不要罗列所有数据行，只挑最有信息量的 2-3 条讲。
```

### 实测效果（同一分析任务，2 次）

| 指标 | 改前 | 改后 | 变化 |
|---|---|---|---|
| 输出 tokens | ~600 | ~250 | **少 2.4×** |
| 耗时 | ~3.65s | ~1.75s | **快 2.1×** |
| 质量抽查 | — | 结论加粗 + 数据表格 + 2-3 条要点 | 信息密度反而更高 |

### 这次改动学到什么

**"简洁"不是约束，"≤250 字"才是。** 把主观形容词换成可计量的数字，模型才会真的执行。
而且字数限制必须**配上豁免项**（表格不计入）——否则模型为了凑字数会把表格砍掉，反而丢信息。

## 2. SQL Agent：把受控工具提到自由 SQL 之前

**提交**：`50cd77d`
**文件**：`harness/orchestration/multi/agents.py`

### 问题

工具清单里 `run_query`（LLM 自由写 SQL）排在前面，模型自然优先用它。
但自由 SQL 的出错面更大——字段名猜错、聚合写错、越权风险都得靠护栏事后拦。

### 改前

```
4. run_query — 在 SQLite 上执行 SELECT（只读）
5. search_memory — 检索长期对话记忆……
```

### 改后

```
4. query_table — 受控取数：填结构化取数单查单表（过滤/聚合/排序/取前 N），不写 SQL，更安全
5. run_query — 在 SQLite 上执行 SELECT（只读），多表 JOIN 或 query_table 覆盖不了时用
6. search_memory — 检索长期对话记忆……
```

### 效果

- 单表聚合类查询改走**结构化取数单**，SQL 由代码拼，**不靠模型发挥**
- `run_query` 降级为"覆盖不了时再用"，定位更清楚

### 这次改动学到什么

**提示词里的顺序就是优先级。** 想让模型用更安全的路径，最省事的办法是把它排到前面，并在描述里写清"什么时候才用另一个"。

## 3. Jev 路由：补上 Agent 职责，修误判

**提交**：`4902f26`
**文件**：`harness/orchestration/multi/nodes.py: _route_via_jev`

### 问题

路由改成 Jev 之后，它把「提成制度」这类**制度问题误判成需要澄清**。

根因：提问时只问了"这个请求需要「{agent}」Agent 吗？"，**没告诉它每个 Agent 是干什么的**。它只能靠 Agent 名字猜。

### 改前

```python
questions = [
    {
        "id": f"need_{agent}",
        "type": "boolean",
        "prompt": f"这个请求需要「{agent}」Agent 吗？",
    }
    for agent in _ROUTE_AGENT_MENU:
]
```

### 改后

补上 **Agent 菜单（每个 Agent 的职责描述）+ 关键规则**，问题里带上职责：

```python
"prompt": f"这个请求需要「{agent}」Agent 吗？它的职责是：{desc}"
```

### 实测效果

| 输入 | 改前 | 改后 |
|---|---|---|
| 提成 / 年假 | ❌ 误判为 clarify | ✅ → strategy |
| 数据查询 | — | ✅ → sql |
| 「帮我看看数据」| — | ✅ → clarify（正确） |

### 这次改动学到什么

**决策模型不是全知的——你给它的标签越模糊，它越靠猜。** 补上职责描述这种"便宜信息"，比换模型有效。

## 4. System Prompt：把写操作规则写死

**提交**：`7f83f36`
**文件**：`harness/context/system_prompt.py`

### 问题

Agent 有能力生成 SQL 脚本，但**没有明确的写操作边界**。模型可能生成 `UPDATE` / `DELETE`，或者编造用户没给的字段值。

### 改后新增的规则

```
用户要做配置变更时，先生成脚本，不要直接改库。

4. 不支持 UPDATE / DELETE / DROP / ALTER，也不要编造用户没给的字段值

- 插入数据先生成 dry-run 脚本；直接执行必须走 run_insert 和人工审批
```

### 效果

- 写操作**在提示词层就先收窄**，不依赖下游护栏兜底
- 明确"插入必须先 dry-run、执行必须走 `run_insert` + 人工审批"——与 HITL 机制对齐

### 这次改动学到什么

**安全边界要写在提示词里，但不能只写在提示词里。**
提示词负责"让它不想写"，`guard_sql()` + HITL 负责"写了也执行不了"——**两层都要有**。

## 汇总

| # | 改动 | 类型 | 实测 |
|---|---|---|---|
| 1 | Analysis 长度硬约束 | 输出长度 | tokens 少 2.4×、耗时快 2.1× |
| 2 | SQL 工具优先级 | 降低自由发挥 | 单表聚合改走受控取数单 |
| 3 | Jev Agent 菜单 | 修复路由误判 | 提成/年假 → strategy ✅ |
| 4 | 写操作规则 | 安全边界 | 与 HITL 对齐 |

**共同点**：4 次改动都不是"把提示词写得更长"，而是**把模糊要求换成明确规则**——
数字、顺序、职责、边界，每一条都可验证。

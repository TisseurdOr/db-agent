## 案例 1｜路由把「提成制度」判成了"需要澄清"

**提交**：`4902f26`　**类型**：误判

### 现象
用户问提成制度，Router 却判定"问题不含糊，但需要澄清"，反问用户 —— **它压根不该问**。

### 根因
路由交给 Jev 之后，提问只写了：

```
这个请求需要「strategy」Agent 吗？
```

**没有告诉它 strategy 是干什么的。** Jev 只能靠 Agent 名字猜职责，自然判错。

### 修法
补上 **Agent 菜单**：每个 Agent 的职责描述写进问题里。

```python
"prompt": f"这个请求需要「{agent}」Agent 吗？它的职责是：{desc}"
```

### 验证
| 输入 | 结果 |
|---|---|
| 提成 / 年假 | ✅ → strategy |
| 数据查询 | ✅ → sql |
| "帮我看看数据" | ✅ → clarify（这个才对）|

### 学到什么
**决策模型不是全知的 —— 标签越模糊，它越靠猜。** 补"职责描述"这种便宜信息，比换模型有效。

## 案例 2｜自学习拿错了别人的 SQL（并发串扰）

**提交**：`60e0cdc`　**类型**：并发 Bug

### 现象
多个请求同时进来时，自学习模块会**把 A 用户的 SQL 记到 B 用户的账上**。
单请求测试永远发现不了。

### 根因
`_last_successful_sql` 用的是**进程级全局 dict**：

```python
_last_successful_sql = {}   # ← 全局，多请求共享
```

并发时互相覆盖。

### 修法
改成 `ContextVar`，按请求上下文隔离：

```python
_last_successful_sql: ContextVar = ContextVar("last_successful_sql")
```

并且钉了注释：**同步 handler 必须在当前 event loop 线程内直接调用**，否则改回 `to_thread` 会静默失效。

### 验证
并发场景下不再串扰；相关用例转绿。

### 学到什么
**"能跑通"和"并发下能跑对"是两件事。** 全局可变状态是并发 Bug 的头号来源——它平时不发作，压力上来才现形。

## 案例 3｜single 模式号称"挂全量工具"，实际少了 5 个

**提交**：`01bec62`　**类型**：能力不对齐

### 现象
同一个问题，multi 模式答得出来，**single 模式答不出来**。

### 根因
single 模式号称挂全量 tools，实际缺了：

- `discover_relevant_schema`（SQL Agent 的**优先调用**工具）
- 4 个数仓工具（`list/describe/query_warehouse`、`query_period_comparison`）

共缺 5 个（15 → 应为 20）。

**顺带发现第二个坑**：`discover_relevant_schema` 在没配 `EMBEDDING_API_KEY` 时直接抛 `KeyError`，
**绕过了代码里本来写好的降级提示**「索引未就绪，请改用 list_tables + describe_table」。

### 修法
- 补齐 5 个工具（15 → 20）
- 把 `KeyError` 改成友好降级
- 新增 `tests/test_single_tools_bundle.py`（工具覆盖 / handler 齐全 / 降级）**防回归**

### 学到什么
**"两条路能力应该一致"这句话，必须用测试钉住。** 靠人记得补，一定会漏——
这个 case 最后是靠一条断言"single 的工具集必须包含 required 集合"来兜底的。

## 案例 4｜花了 50 倍时间，检索质量一点没涨

**提交**：`015faa5`　**数据**：`logs/ablation_results.json`

### 现象
代码里默认开着 HyDE + rerank 两个"高级检索技巧"。**没人验证过它们到底有没有用。**

### 做法（消融实验）
同一份 golden set（20 正例 + 10 负例），**一次只开一个开关**：

| 配置 | hit@1 | hit@3 | MRR | 耗时 | LLM 调用 |
|---|---|---|---|---|---|
| 裸向量 | 0.85 | 1.0 | 0.925 | **5.9s** | 0 |
| +HyDE | 0.85 | 1.0 | 0.925 | 116.3s | 30 |
| +HyDE+rerank | 0.85 | 1.0 | 0.925 | **290.2s** | 60 |
| +混合(BM25+RRF) | 0.80 | 0.9 | 0.864 | 5.9s | 0 |

### 结论
**零提升，慢 20~50 倍。** 连混合检索也是负的（hit@1 从 0.85 掉到 0.80）。

### 修法
把 HyDE / rerank **默认关掉**，改成环境变量按需打开：

```bash
RAG_USE_HYDE=1      # 文档量大、提问用词与文档差异大时再开
RAG_USE_RERANK=1
```

### 学到什么
**"教程里说有用"不等于"在我这里有用"。**
这个案例的价值不在"我加了高级检索"，而在 **"我验证了它，发现问题，然后把它关掉了"** ——
而且关掉是可回退的（一个环境变量），不是把代码删了。

## 1. 数据治理 Multi-Agent Harness（主力项目，必被深挖）

### 1.1 开场总述（定稿，60~90 秒）

这个项目是给银行数据治理团队做的多 Agent 系统。背景是在 OCC 监管要求下，数据治理团队每天要人工做 feed 对账、血缘查询、load 监控和变更确认。
【重点】核心矛盾用一句话说——job 成功是表面的，数据是不是真正落地才是关键。这些重复的人工动作，正是监管最想用自动化替代的部分。
我的做法是用 LangGraph 搭了一个 10 节点的 StateGraph，拆了 6 个专业 Agent，职责严格隔离：SQL Agent 只查数不分析，Analysis Agent 只分析不查库，Strategy Agent 只查知识库，DataQuality Agent 只报数据质量、不下结论，HBase 和 Hive Agent 各自生成对应存储的方言。【停顿】为什么这么拆？因为同一个 Agent 既取数、又质检、又下结论，上下文和权限会互相干扰，出了问题也说不清是哪个环节的责任。

请求进来先过 Router，四层决策：硬规则、历史继承、LRU 缓存，最后才交给模型。置信度低于 0.7 就进 Reflection 反思，最多两次，再不行就重新规划一次，防止死循环。敏感操作走 Checkpointer 加 interrupt，【重点】暂停等人工确认，确认完从断点继续跑。

还有两个我比较自豪的点。一个是自学习闭环：成功的 SQL 在 run_query 工具层直接捕获，经过 dry-run 质量门校验后回流到样例库，下次查询直接复用。另一个是可评测：35 条用例、独立模型评分，33 条通过；通过率下降超过 5 个百分点会自动告警，防止改代码把系统改坏了还不知道。

### 1.2 必问 Q&A（定稿）

**Q1：为什么用 LangGraph？它解决了什么问题？**
答：三个东西。第一是循环——Agent 本质是 ReAct 循环，LangGraph 把循环和状态管理做成了图，比手写 while 循环可控；第二是持久化——每个节点状态都存进 Checkpointer，任务中断可以从断点恢复；第三是中断恢复——配合 interrupt 实现 HITL，敏感操作暂停等人工确认。这三个是我真正用到的。

**Q2：一条 query 完整走一遍是什么流程？**
答：用户输入先进 guard_input 过输入护栏，然后 Router 分派。比如"华东地区销售额多少"，硬规则识别出是查数，Router 分给 SQL Agent，plan 里写清楚任务。SQL Agent 先 discover_relevant_schema 定位相关表和字段，再从样例库 few-shot 检索相似查询，模板命中就直接填槽，没命中才让模型生成 SQL。生成后过置信度门——6 项自评，表名、列名、JOIN、WHERE 语义、聚合、安全性，低于 0.7 暂停请用户确认。确认后走 run_query 执行，工具层做权限校验，结果截断加本地统计摘要。如果要对比分析，Analysis Agent 接过去出结论。整个过程每个节点都写 Trace。

**Q3：四个 SQL 安全机制怎么区分？**
答：guard_input 是输入层，在调模型之前拦 prompt injection 和危险 SQL 特征；guard_sql 是 SQL 层，检查是不是 SELECT、有没有写操作关键字；rewrite_sql 是权限层，行级隔离，自动追加 WHERE dept_id=X；guard_output 是输出层，正则检测敏感信息，防止模型把不该说的说出去。前三个是硬拦截，置信度门是软兜底，让模型先自评再决定要不要执行。（🟢 详见 `平安面经.md` 第 3 节）

**Q4：DataQuality Agent 放在哪个位置？**
答：在查询路径上、先于 Analysis。首次查询时自动扫描日期连续性、关键字段 NULL 比例、异常值和状态分布，给下游分析做质量预检，扫描控制在 5 条 SQL 以内。核心就是"先看数据能不能用，再谈分析"。（🟢 详见 `平安面经.md` 第 4 节）

**Q5：并发和限流怎么做？（🟡 gap 定稿，只说方案别说已实现）**
答：这块我目前是方案层面的设计，代码里还没完全落地，我说一下思路。一是信号量控制同时进行的 Agent 任务数，防止多用户并发打满资源；二是 token bucket 限流，保护下游 API 配额；三是给每个节点设超时和熔断，模型服务连续失败就快速失败、返回降级文案，而不是一直重试。（⚠️ 强调是设计，不是实际跑过的量级）

**Q6：RAG 召回和精排怎么配合？**
答：召回阶段我会先改写查询，把口语化问法转成规范表述，然后并行召回、去重；精排阶段按相关性打分重排，取 Top-K 进上下文。召回要的是别漏，精排要的是别错。项目里 few-shot 样例库的检索也是这个思路，相似度阈值 0.35，低于阈值就不给样例，宁缺毋滥。（🟢 详见 `平安面经.md` 第 6、7 节）

**Q7：职责隔离除了拆 Agent，还在哪一层落地？（白名单 + RBAC，简历点）**
答：两层。第一层是工具白名单——每个 Agent 只能挂载自己职责范围内的工具，比如 SQL Agent 挂 run_query 和 schema 相关，Analysis Agent 不挂任何查库工具，从能力上就杜绝了跨职责串扰。第二层是 5 角色 RBAC 行级隔离——rewrite_sql 自动注入 WHERE dept_id=X，同一张表，不同部门只能看到自己部门的数据。（🟢）

**Q8：Analysis Agent 怎么保证分析质量？（简历点：结论先行 + 异常标注）**
答：结论先行——先给结论再给依据，不是罗列一堆数字让用户自己看。它会主动跨地区、时间、部门、产品做对比，发现异常就标注出来，比如"这个月华东环比下滑 20%，异常"。而且它不查库，数据全部来自上游 Agent 的查询结果，职责边界很清楚。（🟢）

**Q9：可观测和评测怎么做的？（简历点：JSONL + Opik 双写）**
答：双写 Trace——本地 JSONL 做审计留存，Opik 看执行树和反馈，每个节点记录耗时和成本。评测 35 条用例分四类：护栏 6 条、路由 12 条、输出 5 条、边界 10 条，由独立模型评分，33 条通过；通过率比上次降超过 5 个百分点就自动告警。（🟢）

## 2. NL2SQL 查询引擎

### 2.1 开场总述（定稿，50~70 秒）

这个项目解决的是：业务人员用自然语言查数，不用手写 SQL。如果直接让模型生成 SQL，有两个问题：一是会编造列名，二是得把完整库结构塞进提示词，又贵又难约束。

我做了四件事。第一，意图分流——先判断是闲聊、元问题还是真查数，闲聊根本不进查数链路，不检索也不写记忆。第二，上下文工程——【重点】不把整个库的 schema 塞进去，先做 Schema Linking 定位相关表和字段再注入，取值少的列补充可选值，few-shot 从已验证的样例库里检索相似查询，相似度阈值 0.35。第三，记忆和预算——三层记忆分层，工作记忆、短期窗口、长期向量；32k 的 token 预算，用到 70% 就触发分层压缩，最近 6 条保留原文、7 到 14 条成对摘要、更早的收成全局摘要，而且两套摘要不同时注入，避免互相干扰。第四，安全和自愈——输入拦注入，输出正则检测敏感信息，SQL 执行失败最多自动改写两次，模型接口异常按递增间隔重试。

结果上两个数字：【重点】Prompt Caching 让 token 成本降了 99.5%；高频问法走模板优先链路，不用每次从零生成。

### 2.2 必问 Q&A（定稿）

**Q1：Prompt Caching 99.5% 怎么做到的？（🟡 要点见 `平安面经.md` 第 8 节）**
答：背景是 DeepSeek 的 context caching，缓存命中的价格大概是 miss 的 1/50 到 1/120。我做的事是保证前缀能逐字节命中缓存——系统提示词和工具描述是静态的，通过结构优化让它们固定在最前面、逐字节一致，动态内容全放后面；再加一层 Router 的 LRU 缓存，相同 query 直接命中 plan，连模型都不用调。99.5% 是项目里实测的成本下降比例。

**Q2：三层记忆怎么分层、怎么防污染？（含元问题处理，简历点）**
答：工作记忆是当前这次任务临时用的；短期窗口保留最近几轮对话原文；长期记忆里，结构化偏好存 SQLite，对话片段存向量库。中间有个记忆控制器按 query 类型分流——闲聊和元问题不写向量库，防止污染；元问题比如"刚才问了什么"，不走语义检索，直接按时间倒序取最近的业务问答。长期检索时，口语化问法先改写、再召回、再重排。（🟢）

**Q3：15 个原子工具怎么组织？工具描述怎么来的？**
答：工具分几类：Schema 定位、数据查询、结果分析、存储方言、知识记忆、指标口径、模板。工具描述用 @tool 装饰器从函数 type hints 和 docstring 自动生成 JSON Schema——参数名改一处，schema 自动跟着变，不用手写 25 行 schema 去配一个 5 行的函数。（🟢 single 挂全量，multi 额外挂 discover_relevant_schema + lookup_metric 共 17 个）

**Q4：简历写"单次查询最多一轮工具调用"，代码对不上？（🟡 澄清稿）**
答：这个我澄清一下，实际是有限轮数的 ReAct loop，max_turns 等于 10 兜底防死循环。我想表达的是，每轮里可以把无依赖的工具调用合并到一起发，比如 list_tables 和 describe_table，减少往返。简历那句是我的表述不准。

**Q5：SQL 失败怎么自愈？**
答：run_query 失败不抛裸异常，而是返回结构化的 error、retryable、hint，提示 Agent 先 describe_table 核对表名字段名再重写，最多改两次，max_turns 兜底。这样模型能自己修，而不是直接崩给用户。（🟢）

## 3. Olympus Core 数据交付保障（花旗本职，问"和 Agent 有什么关系"时讲）

### 3.1 开场总述（定稿，45~60 秒）

这是花旗 Global 战略级的大数据底座，一个批发数据的再分发平台。上游多系统的交易、持仓、事件数据进来，经过清洗、校验、路由，形成 Markets 的权威副本，再按授权分发给风控、合规、总账、流动性和监管报送这些下游。【重点】我负责的是 Kafka 实时流和 SFTP 批量两条通道的数据质量保障，覆盖 load、validation、dispatcher、monitor、recon 全链路。调度层是 Autosys，执行层是 Spark 加 HDFS。四条业务线——DGB、BKB、Opportunity、DDA-checking——长期保持双通道稳定交付。这个平台的容错要求很直接——漏数、延迟、口径漂移，都会直接中断下游的风控和合规，所以准时性和完整性是硬指标。

### 3.2 必问 Q&A（定稿）

**Q1：recon 对账怎么做？【重点】这是"0 事故"的底气，必背**
答：三层。第一层行数——上游 N 条、下游 N 条，保证完整性，不少不重；第二层 checksum 哈希——逐条算哈希比对，字段被截断或改坏，哈希一定变，保证内容一致；第三层金额加总 control total——关键金额列 SUM 上游等于下游，保证准确性。对不上先自动重拉，还不行就进差异报告，报业务人工兜底。SOX 审计要求每次 load 按 batch_id、源文件、offset 可追溯。

**Q2：SFTP 和 Kafka 两条通道对账有什么不同？**
答：SFTP 是文件，自带总行数、checksum、文件大小，直接对"内容对不对"；Kafka 是流，没有总行数，靠 offset 加源序列号查"有没有漏"——跳号就是漏消息，消费端用唯一键约束做幂等防重。

**Q3：Autosys 和你的监控什么关系？**
答：Autosys 负责按时触发批量 feed。但【重点】Autosys 绿了只说明 job 启动过，不代表数据按 SLA 落到了目标路径。有没有按时、有没有完整，还得靠 recon 加 monitor 验——"调度成功不等于交付成功"。

**Q4：日常监控巡检和异常处理怎么做？（简历点：监控与巡检 + 异常处理）**
答：monitor 盯作业状态和落地延迟，超过 SLA 就告警；每天有巡检清单，覆盖四条业务线的准时性和完整性。异常分两类处理：漏数先自动重拉，重拉不行进 break report 报业务兜底；错数靠三层 recon 暴露，定位到 batch 回退重跑。（🟢）

**Q5：Cancel & Correct（交易更正）？**
答：这个业务线我实际没覆盖。我这边只接到"重拉加三层 recon"，交易更正的具体流水线我没有做过，不编。

**Q6：结尾金句（被问"为什么 0 事故"时收尾）**
答：三年零事故不是靠人盯，是靠三层自动对账加全链路可追溯——漏一条、错一笔、晚一批，都在对账环节自动暴露，而不是等下游投诉才发现。

## 4. Metadata 驱动配置自动生成引擎

### 4.1 开场总述（定稿，40 秒）

背景是，源表字段一变，就得手工改多张生产脚本和配置表，流程长，容易漏改错改，而错误配置一旦写进 Olympus，会影响多条业务线入仓。【重点】我独立做了个全栈工具，Spring Boot 加 React。核心思路是：一条 feed 的配置就由 7 个关键字段决定——feed 名字、源文件名、源路径、目标路径、窗口开始、窗口结束、SLA。工具从 job_description、source、data 这些源表自动提取这 7 个字段，生成 7 张配置表、约 210 个字段的改库脚本。效果是常见变更从 2 小时降到 10 分钟，提效 92%，组内常态在用。

### 4.2 必问 Q&A（定稿）

**Q1：7 个关键字段是哪些？（背熟，别报第 8 个）**
答：feed-name、source-file、source-path、target-path、start time、end time、SLA。发送时间并进 start time 加 Autosys 调度，不是一个独立字段。

**Q2：Autosys 和 SLA 什么关系？**
答：Autosys 按 feed-name 和窗口拉源、推目标；SLA 是必须送达的时限，给 monitor 判断晚批用。

**Q3：生成的脚本怎么保证正确？（🟡 gap 定稿）**
答：我当时的做法是生成后人工 review 一遍再执行，没有做全自动 dry-run 和回滚，这是可以改进的点。如果要上生产，我会加两层：先在影子表上 dry-run 验证字段和依赖，再包事务、出错自动回滚。

**Q4：怎么避免影响多业务线？（🟡 gap 定稿）**
答：实际是变更隔离——一次只改一条 feed 的配置，先在这条业务线验证再放量；自动化回滚当时没做，靠的是变更前备份原配置。

## 5. 权限体系建设 Entitlement

### 5.1 开场总述（定稿，25~35 秒）

多业务线共享 Olympus Core 的时候，必须按人员、组织、用户组做精细化授权，不然过不了内部合规审计。【重点】我参与了 Entitlement 系统的搭建：登录认证，加上个人、组织、用户组三层细粒度授权，让四条业务线在共享平台下访问可控。最后通过了内部合规审计。

### 5.2 必问 Q&A（定稿）

**Q1：为什么分三层？**
答：不同粒度管不同范围。个人是单点权限，给具体的人；组织是部门级，整个部门一个策略；用户组是跨组织的角色和岗位，比如所有分析师。三层叠加，既灵活又可控。

**Q2：和你 db-agent 里的 RBAC 有什么异同？【重点】主动对比，加分**
答：花旗的 Entitlement 是表级、接口级授权——决定能不能访问某个资源；db-agent 的 RBAC 是行级授权——能访问，但只能看 dept_id 匹配的行，通过 rewrite_sql 自动注入 WHERE。行级比表级更细，因为同一张表，不同部门看到的数据应该不一样。（🟢）

## 6. 共享入仓管道性能治理（Spark）

### 6.1 开场总述（定稿，40~50 秒）

共享入仓管道出现 Spark 数据倾斜，Opportunity 作业不稳定，下游超时堆积。【重点】我定位到根因是 join key 分布不均——join key 是 timestamp，开盘和整秒的数据扎堆，默认 Sort-Merge Join 会把同一时刻的记录全收进一个分区，那个 Task 就出现 Stage 长尾。这是大事实表 join 小维表，我做了两件事：调整分区策略，并把小表做成广播变量，走 Broadcast Hash Join——大表不再按 timestamp shuffle，热时刻不会砸在单个 Task 上。作业稳住，下游不再超时，最后整理成可复用方法论报告。

### 6.2 必问 Q&A（定稿）

**Q1：怎么定位数据倾斜？**
答：Spark UI 看 Stage 里少数 Task 的时长和 shuffle 读远大于中位数，基本就是倾斜了；再对 join key 做 count 看占比，确认是哪个 key 扎堆。我这个 case 的 key 是 timestamp，开盘和整秒扎堆。

**Q2：为什么广播变量能解？**
答：大表 join 小表，把小表 broadcast 到每个 executor 走 Broadcast Hash Join，大表不再按 key shuffle，每个 task 本地扫自己那片大表，加内存里的小表哈希——shuffle 没了，倾斜就没了。

**Q3：什么时候广播解不了？（反追问，讲出边界才显深度）**
答：三种情况。第一，小表太大塞不进 executor 内存，硬广播会 OOM——默认阈值大概 10MB，维表几十上百 MB 优化器还是会走 Sort-Merge，要先看体积再决定。第二，repartition 打不散热 key，Join 还会按 key shuffle 回去。第三，两边都是大表，才需要加盐——大表 key 加随机后缀、小表复制 N 份。这次小表能进内存，广播就够，加盐我没用。

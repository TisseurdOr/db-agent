## 1. LangGraph 三件事（平安 JD 点名：循环图 / 状态持久化 / 多智能体协作）

**Q：为什么上图工作流而不是手写 ReAct？循环在哪、状态怎么持久化、中断恢复怎么做？**

定稿：
- **循环**：reflection（最多 2 次）+ replan（最多 1 次）是条件边回退，形成「执行→反思→回退重试」；所有循环都有 max_turns 硬上限（single=10 / multi=8）防死循环。
- **持久化**：State 是内存里节点间流动的工作数据（TypedDict）；Checkpoint 是 AsyncSqliteSaver 把 State 快照落盘到 agent_state.db，进程重启后按 thread_id 读回最新 checkpoint 继续。
- **中断恢复**：interrupt() 在敏感 SQL / 置信度 <0.7 处暂停，main.py 问 y/n，resume(approved) 恢复。这是手写 ReAct loop 做不到的。

⚠️ 易错：State ≠ Checkpoint。State 是内存工作数据，Checkpoint 才是 SQLite 快照。

## 2. 完整链路（面经原题：query 从进来到返回）

**Q：一个 query 进来，完整走哪些模块、每个模块做什么？**

定稿顺序（每个一句）：
`Router 意图分流 → schema_discovery 定位表字段 → SQL 生成（5 道闸门）→ run_query 执行 → 置信门/反思 → 记忆写入 + 成功 SQL 回流样例库`

- Router：硬规则 → 历史继承 → LRU(100) → LLM 四层决策，分派到 SQL/Strategy/Analysis 等 Agent。
- schema_discovery：语义检索相关表+字段，低基数列补可选值。
- SQL 生成 5 道闸门：guard_input → few-shot → guard_sql → 置信门(<0.7 HITL) → reflection + guard_output。
- 超时：某节点超时 → replan（最多 1 次）重排，防死循环。

## 3. 四个 SQL 安全机制区分（最易混，反复张冠李戴）

| 机制 | 时机 | 动作 | 防什么 |
|---|---|---|---|
| guard_input | 输入 | 正则拦注入/写 SQL | 用户输入注入 |
| guard_sql | 执行前 | **检查** SQL，只放行 SELECT | 写操作 / 多语句 / 系统表 |
| rewrite_sql | 执行前 | **改写** SQL，加 `WHERE dept_id=X` | 行级越权（看别的部门） |
| guard_output | 输出前 | **脱敏** PII + 检测提示词泄露 | 敏感信息泄漏 |
| 置信门 | 执行后 | 从结果抽 SQL，LLM 自评 6 项，<0.7 HITL | 看着对其实错 / 答非所问 |

⚠️ 关键：guard_sql 是「检查+拦截」不改写；「改写加 WHERE」是 rewrite_sql；「防泄漏」= rewrite_sql（行）+ guard_output（输出），跟 guard_sql 无关。

## 4. DataQuality 位置

**Q：数据质检 agent 在链路哪个位置？**

定稿：**执行后**的对账质检。自己发 ≤5 条 SQL 扫日期连续性 / NULL 比例 / 异常值 / 状态分布，**只报质量不下结论、不改数据**，产出喂给 Analysis 做质量预检。不是执行前的"数据清洗"（清洗是写操作，全链路只读）。

## 5. 并发 / 限流（弱项，平安工程岗必问）

**Q：100 个用户同时打进来会发生什么？并发控制 / 限流 / 慢查询隔离怎么做的？**

定稿（诚实：demo 没上生产，四样是 gap，用大数据背景接住）：
1. **并发上限**：`asyncio.Semaphore` 限同时查询数（如 10）——等价于 Spark 资源队列上限。
2. **主动限流**：token bucket 控 TPM/RPM，不等 429 再退避（现在只有 retry.py 被动退避）。
3. **慢查询隔离**：`asyncio.wait_for` wall-clock 超时 + max_rows，慢查询超时 kill；复杂分析进优先级队列。
4. **熔断降级**：连续失败 N 次熔断，切备用模型。

策略：已做的报细节（asyncio 全链路 / acall_with_retry / max_turns），gap 报方案+为什么。信号量=资源队列、限流=背压、熔断=容灾，这是大数据背景的差异化优势。

## 6. RAG 召回 vs 精排（面经原题）

**Q：召回和精排分别用什么模型？技术路线差异？为什么不用 cross-encoder？**

概念（双塔 vs 交叉）：

| | 召回 | 精排 |
|---|---|---|
| 架构 | 双塔 bi-encoder | 交叉 cross-encoder |
| 做法 | embedding 分别编码，算余弦相似度 | query+doc 拼一起，token 级交互 |
| 特点 | 快、粗 | 慢、准 |

项目真实状态（别念简历）：生产是 **ChromaDB 裸向量 recall + 阈值 0.5**（负例评测暴露 0.3 过低，调到 0.5）；**HyDE + LLM rerank 是死代码没接线**；消融证明 rerank 各 +0 点、成本 +18 倍（hit@3 已 100% 封顶测不出 + rerank 只重排不改候选集，拦不住该拒的噪声）。

定稿：
> "召回用 embedding 模型编码向量算相似度，阈值 0.5 卡噪声；精排我实现了 HyDE + LLM rerank，消融发现 +0 点、成本 +18 倍，生产保持裸向量；需要精排时换 cross-encoder。"

## 7. few-shot 样例库构建 + schema_discovery（面经原题）

**Q：SQL 数据集怎么构建？新表没训练怎么保证 SQL 准？**

定稿：
- **样例库**：自学习回流——run_query 成功 SQL 自动捕获 → dry-run 质量门校验 → 回流样例库。一条样本 = {自然语言问题 → 已验证 SQL}，检索按相似度 0.35 召回注入。few-shot 检索失败返回空串、不挡主流程（数据面软增强失败降级）。
- **新表不靠训练**：schema_discovery 每次**动态语义检索**相关表+字段，把真实表结构 + 低基数列可选值注入 prompt + few-shot 召回相似已验证 SQL。新表只要 schema 元数据更新了就能被搜到，天然适应、不用重训。
- **意图识别**：生成式（硬规则优先 + LLM 生成兜底），不是监督分类。意图类别：闲聊 / 元问题 / 查数（Multi-Agent 更细：闲聊/元问题/制度查询/纯查数/对比分析）。

## 8. Prompt Caching 99.5%（简历数字，最易被追）

**Q：99.5% 怎么算？总成本还是单项？什么机制、什么条件生效？**

⚠️ 数字纠错：Anthropic cache read 是 0.1×（降 90%），**不是 99.5%**；DeepSeek context caching 折扣深（cache hit 是 miss 的 1/50~1/120，降 98%~99.17%），所以 99.5% 只在 DeepSeek 上成立。

定稿（不纠结服务商，数字说约 99%）：
> "Prompt 缓存我是这么接的：把 system prompt 和工具描述稳定放在请求前缀，服务端命中缓存后，这部分输入 token 按 cache hit 价计费——cache hit 大概是 miss 的 **1/100**，所以 prompt 输入成本降了**约 99%**。缓存本身是服务商特性，我负责的是 prompt 结构优化、保证前缀逐字节一致让命中率最大化；另外我自己写的是 **Router LRU**，缓存路由决策结果，省的是每次路由那次 LLM 调用。具体我 demo 跑在 DeepSeek 上，它叫 context caching，固定前缀自动命中。"

被追问"简历写 99.5% 你刚说 99%"：答「cache hit 折扣在 1/50~1/120 之间，看模型和时段，取约值 99%，四舍五入到 99.5% 也成立」。

⚠️ 概念：缓存是**服务商特性**，不是自己写的。自己做的是 prompt 结构优化 + Router LRU。DeepSeek 自动缓存（无需标记），Anthropic 需手动 cache_control。生效条件：前缀 ≥1024~2048 tokens、逐字节一致、TTL ~5 分钟。

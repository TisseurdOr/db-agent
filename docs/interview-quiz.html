一、Harness 工程哲学 4 题

Q1 "你说你做的是 Agent，实际上做的是什么？Agent 和 Harness 的区别？"

标准回答：

"我做的是 Harness，不是 Agent。Agent = 模型 + Harness。

Agency（感知、推理、行动的能力）来自模型训练——数十亿次梯度更新学到的东西，不是我代码编出来的。Harness 是我造的——Tools（14 个）、Knowledge（制度文档、语法模板）、Permissions（5 角色 + 表级/行级隔离）。

模型做决策，Harness 执行。模型做推理，Harness 提供上下文。模型是驾驶者，Harness 是载具。我没有训练模型，我造的是让模型在数据库领域高效工作的环境。"

Harness 公式：

Harness = Tools + Knowledge + Observation + Action Interfaces + Permissions
面试要点：不要说我"基于 harness 思想做 agent"，要说"我逆向工程了 Claude Code 的 12 个 harness 机制，落地到大数据场景"。
"我基于 harness 的思想做了个 agent" — 听起来 harness 只是方法论，没有拆开。

Q3 "Harness vs LangChain/AutoGPT 这类 Agent 框架的本质区别？"

标准回答：

"那些框架试图'编排智能'——用 if-else 分支、节点图、硬编码路由逻辑把 LLM 调用串起来。LLM 被楔在里面当美化的文本补全节点。那不是 Agent，是有个宏大妄想的 shell 脚本。

Harness 哲学相反：模型来做决策，harness 只是载具。我不编智能，我给智能提供手（Tools）和眼睛（Observation）和边界（Permissions）。

核心区别：谁做决策。LangChain 是代码决定下一步做什么——固定的节点图。Harness 是模型决定下一步做什么——while stop_reason=='tool_use'，模型自己选 tool。"

面试要点：这不是贬低 LangChain，是说清楚架构哲学的差异。LangGraph 本身只是编排工具，db-agent 用它做的是 harness 层的编排，不是业务逻辑的 if-else。
Q4 "你说 Agency 来自模型，那 harness 工程师到底做什么？"

五个职责：

  1. 实现工具 — 给 Agent 双手。原子化、可组合、描述清晰。
  2. 策划知识 — 给 Agent 领域专长。按需加载（Skills），不前置塞入。
  3. 管理上下文 — 给 Agent 干净的记忆。Subagent 隔离、压缩、持久化任务。
  4. 控制权限 — 给 Agent 边界。沙箱化、审批、信任边界。
  5. 收集任务数据 — 真实部署中的感知-推理-行动轨迹，是微调下一代 Agent 的原材料。

"你不是在编写智能。你是在构建智能栖居的世界。造好 Harness，Agent 会完成剩下的。"

二、Agent Loop & Tool 系统 5 题

Q5 "Agent Loop 的核心代码是什么？用伪代码讲。" 
messages = [{"role": "user", "content": user_msg}]

for turn in range(max_turns):
    response = client.messages.create(
        model=MODEL, system=SYSTEM,
        messages=messages, tools=TOOLS,
    )
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason != "tool_use":
        return text_content  # 模型觉得该停了

    # 执行每个 tool call
    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            handler = TOOL_HANDLERS[block.name]
            output = handler(**block.input)
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": output,
            })
    messages.append({"role": "user", "content": tool_results})

关键设计决策：

  • temperature=0：Agent 选 Tool 必须确定，不能随机
  • max_turns=10：单 Agent 模式。multi agent 里每个 agent max_turns=8
  • 结构化错误：Tool 失败不 crash，返回 {"error": ..., "suggestion": ...} 让模型自己纠正
  • Tool 结果截断：超过 8000 字符截断，防止 token 爆炸
Q6 "加一个新 tool 要改几处？具体步骤。"

3 步，Agent Loop 零改动：

  1. 定义 tool schema — 在对应 tools/*.py 里加 dict，含 name/description/input_schema
  2. 实现 handler 函数 — 同一个文件里写具体逻辑
  3. 注册到 dispatch map — 在 main.py 的 TOOLS 和 TOOL_HANDLERS 中加一条

如果要让特定 Agent 也能用，再在 multi_agent/agents.py 的 ConfiguredAgent 中添加。

关键架构：streaming_agent() 不依赖具体 tool——tools 和 handlers 通过参数传入：

async def streaming_agent(client, user_msg, system_prompt,
                          tools, handlers, ...):  # ← 调用方传什么就用什么
面试要点："这就是 s02 的 dispatch 模式——循环不用动，新 tool 注册进 map 就行。和 Claude Code 的设计一样。"
Q7 "Tool schema 必须包含哪三个字段？为什么 description 很重要？"

三个必须字段（Anthropic API 要求）：

  1. name — tool 唯一标识符
  2. description — 告诉模型这个 tool 是干什么的、什么时候该用
  3. input_schema — JSON Schema 格式，含 type/properties/required
{
    "name": "run_query",
    "description": "在 SQLite 上执行一条 SELECT 查询，返回结果。只支持只读操作。",
    "input_schema": {
        "type": "object",
        "properties": {
            "sql": {"type": "string", "description": "要执行的 SELECT 语句"}
        },
        "required": ["sql"]
    }
}

description 为什么重要：模型根据 description 决定何时调用哪个 tool。写得太模糊→模型乱调；写得太窄→模型不调。比如 run_hbase 的 description 叫"在本地模拟 HBase 上执行查询"，不是"执行 HBase 命令"——因为实际上跑的是模拟器。

面试要点："你的冒烟测试 test_all_tool_schemas_valid 就是验证这三个字段和 properties/type 格式的。"
Q8 "你用了 streaming 模式，为什么？和非 streaming 的区别？"

streaming 模式的好处：

  • 用户体验：逐字输出，用户看到 Agent "在思考"，信任感来源
  • 实时 tool 调用可见：🔧 run_query... 调用发生时就能看到，不用等完整响应
  • 低首 token 延迟：不用等完整 response 生成完才开始展示

实现细节（agent.py:161-201）：

with client.messages.stream(...) as stream:
    for event in stream:
        if event.type == "content_block_start":
            # tool_use 开始 → 打印 🔧 tool_name...
        elif event.type == "content_block_delta":
            if delta.type == "text_delta":
                print(delta.text, end="", flush=True)  # 逐字输出
            elif delta.type == "input_json_delta":
                tool_use_blocks[idx]["input"] += delta.partial_json  # 累积参数
# stream 结束后 get_final_message() 返回完整解析好的 message

保留非 streaming 版本的原因：供测试和 batch 场景使用——不需要看 streaming 输出。

Q9 "Tool 执行出错时你怎么处理？直接抛异常吗？"

不抛异常。返回结构化错误给模型，让它自己纠正：

# agent.py: _execute_tool()
try:
    result = handler(**tool_input)
    return json.dumps(result, ensure_ascii=False), False
except Exception as e:
    error_payload = {
        "error": str(e),
        "type": type(e).__name__,
        "suggestion": "检查 Tool 参数是否正确，或尝试其他 Tool",
    }
    return json.dumps(error_payload, ensure_ascii=False), True

为什么：SQL 写错、表不存在是正常情况。把错误信息返回给模型，让它自己改正（比如换表名、改 SQL），比直接 crash agent loop 好。这是 lesson 0008 的结构化错误返回原则。

Q11 "短期记忆的 ConversatonManager 怎么工作的？滑动窗口多大？"
  • 窗口大小：10 条消息（max_recent=10）
  • 窗口内：保留原文不动，通过 ConversationManager.messages 存着
  • 超出窗口：调 compress_history() 用 LLM 压缩为摘要，合并到 self.summary
  • 注入方式：build_context() 生成 "[早期对话摘要 - 共 N 轮]\n...\n[最近对话如下]" 注入 system prompt
  • token 估算：token_estimate() 本地字符折算（中文 0.4 token/字），零 API 成本
# 核心逻辑
async def add_message(self, message):
    self.messages.append(message)
    if len(self.messages) > self.max_recent:  # 超过 10 条
        overflow = self.messages[:-self.max_recent]
        new_summary = await compress_history(self.client, overflow)
        self.summary = f"{self.summary}\n{new_summary}"
        self.messages = self.messages[-self.max_recent:]
面试要点：如果面试官问"为什么用 10 不是 20"，答"经验值——太少模型缺上下文，太多 token 浪费。10 条通常覆盖最近 2-3 轮完整交互（每轮 ≈ user msg + assistant response + tool calls），足够维持对话连贯性。"

Q13 "TokenBudget 怎么估算 token？为什么不用 API 的 count_tokens？"

估算公式（token_budget.py:2-9）：

def estimate_tokens(text: str) -> int:
    chinese_chars = sum(1 for c in text if '一' <= c <= '鿿')
    other_chars = len(text) - chinese_chars
    return int(chinese_chars / 1.5 + other_chars / 4)
  • 中文：~1.5 字符/token
  • 英文/代码：~4 字符/token（~0.75 词/token）

为什么不全依赖 API count_tokens？

  1. 在发请求前就要知道——不能等 API 报错才知道超了（API 返回的 usage 是消费记录，你需要的是预算工具）
  2. 零延迟、零成本——本地字符折算 vs 一次网络往返
  3. 端点兼容性——DeepSeek 等兼容端点不一定支持 count_tokens

ConversationManager 也提供了一个精确版 token_count_exact()，调 Anthropic 的 count_tokens API，失败时自动降级到本地估算。

触发压缩的条件：

def should_compress(self, messages):
    used = self.current_usage(messages) + self.system_prompt_tokens + self.tool_defs_tokens
    return used > self.max_tokens * 0.7  # 超过 70% 就预警
Q14 "HybridWindowManager 的四层压缩具体怎么分层？" 
messages = [m1, m2, ..., m20]  # 假设 20 条消息

Layer 0 (底层): 最近 6 条 → 原文不动    messages[-6:]
Layer 1 (中层): 第 7-14 条 → 逐对压缩   messages[-14:-6] → 每 2 条用 LLM 压缩一句话
Layer 2 (顶层): 第 15+ 条 → 全局摘要   messages[:-14] → 所有更早消息压成一段话

注入 system prompt 的格式:
  [早期对话 - 共 N 条]
  （全局摘要）

  [中间过程]:
  - （第7-8条摘要）
  - （第9-10条摘要）
  - ...

  (最近 6 条原文直接保留在 messages 里)

为什么中间层每 2 条压缩一次？

单条压缩 token 浪费（每条都要调一次 LLM），全部压缩丢失细节。每 2 条一组是工程折中——保留足够粒度，控制 LLM 调用次数。

压缩模型：用便宜的 deepseek-v4-flash，不浪费旗舰模型 token。

Q15 "memory_controller 的四种路由策略分别是什么？"
场景判断条件记忆策略

四、权限 & 安全 6 题

Q16 "你的权限系统有几层？每层做什么？"

两层生效 + 一层审批：

层位置作用失败后果
Layer 1 — Softsystem prompt 注入build_permission_context() 告诉 Agent 边界，减少无效调用Agent 仍可能尝试调越权 tool
Layer 2 — Hardtool 执行前check_entitlement() 门禁。过不了直接 deny返回 error 给 Agent
HITLtool 执行中LangGraph interrupt() 暂停等人工审批用户点 y/n 决定

为什么做两层：Soft 层省 token——Agent 知道自己不能查 employees，就不会浪费 LLM 调用来尝试。但 Soft 层不可靠（模型可能不遵守），所以 Hard 层兜底。

表级隔离（check_table_access）：白名单检查——角色 db_tables 列表里没有的表直接拒绝。

行级隔离（rewrite_sql）：SQL 改写——自动追加 WHERE dept_id=X：

# 萧一鸣（市场部经理 dept_id=2）
# 原始: SELECT name, salary FROM employees ORDER BY salary DESC
# 改写: SELECT name, salary FROM employees WHERE dept_id = 2 ORDER BY salary DESC

实现：正则提取 FROM/JOIN 表名 → 匹配 db_row_filter 规则 → 在 GROUP BY/ORDER BY/LIMIT 前插入 WHERE/AND。

"行级隔离会改数据库数据" — 不改数据，只改 SQL 文本。
Q18 "HITL 审批什么场景触发？技术上怎么实现的？"

触发场景：

  • SQL 敏感列：salary、cost、budget（SENSITIVE_COLUMNS）+ 角色 sensitive_check=True
  • HBase 破坏性操作：put、delete、drop、truncate（_HBASE_DESTRUCTIVE_OPS）

实现方式：LangGraph interrupt()

# main.py 中的中断处理
result = await multi_runner.run(user_input, ...)
if isinstance(result, dict) and result.get("__interrupt__"):
    interrupt_data = result["data"]
    print(f"⚠️ 敏感查询需要审批")
    print(f"  用户: {interrupt_data.get('user')}")
    print(f"  SQL:  {interrupt_data.get('sql')}")
    choice = input("  是否继续执行? (y/n): ")
    result = await multi_runner.resume(approved=(choice == "y"))

graph 在 run_query 节点中遇到敏感 SQL 时调 interrupt() 暂停——Checkpointer 保存当前 state → 返回给 main.py → 等用户输入 → resume() 恢复执行。

面试要点："interrupt() 是 LangGraph 的 Human-in-the-Loop 机制——graph 暂停但不丢状态，Checkpointer 保存一切，resume 后从断点继续。"
Q19 "三层 guardrails 分别检查什么？为什么用纯规则不用 LLM？"
层位置检查内容
L1 — 输入护栏LLM 调用前空输入、超长(>2000)、prompt injection（14 个正则）、嵌套 SQL 注入
L2 — SQL 护栏run_query 执行前非 SELECT 拦截、写操作关键字、多语句检测、系统表检测
L3 — 输出护栏Agent 输出后空输出、超长(>8000)、PII 检测（手机/身份证/邮箱/银行卡）、system prompt 泄露

为什么纯规则不用 LLM：

  1. 零延迟——正则匹配是微秒级，LLM 调用至少 200ms
  2. 零 token 成本——每次调用都跑 LLM 检查，成本不可接受
  3. 确定性——正则不会"今天拦明天不拦"
  4. 可调试——误拦了改正则就行，不用调 prompt

PII 检测只警告不拦截的原因：业务数据中合法出现 PII（如订单里的客户手机号）不应被拦。

Q20 代码题："用户的 SQL 是 SELECT name, salary FROM employees ORDER BY salary DESC，role=manager(dept_id=2)，经过 check_entitlement 后会发生什么？"

两件事发生：

  1. SQL 改写（行级隔离）： 
    SELECT name, salary FROM employees ORDER BY salary DESC
→ SELECT name, salary FROM employees WHERE dept_id = 2 ORDER BY salary DESC
  2. 触发 HITL：salary 在敏感列中，manager 的 sensitive_check=True，SQL 被拦截暂停等审批。

执行流程：

check_entitlement(user, tool_name="run_query", sql="SELECT name, salary FROM employees...")
  → authorize_tool(): passed（manager 可调 run_query）
  → check_table_access("employees"): passed（manager 可查全部表）
  → rewrite_sql(): 追加 WHERE dept_id=2
  → needs_approval(): True（salary 在 SENSITIVE_COLUMNS 中）
  → 返回 EntitlementResult(passed=True, sql="SELECT...WHERE dept_id=2...", needs_approval=True)
  → 触发 interrupt() 暂停等审批
"WHERE 放 ORDER BY 后面" — SQL 语法错误。WHERE 必须在 ORDER BY 之前。
Q21 "输入 '帮我删掉 orders 表里的数据' 会被拦吗？为什么？'SELECT * FROM users; DROP TABLE orders;' 呢？"

第一个（自然语言）：不拦。

自然语言中的"删掉"没有匹配 _SQL_WRITE_IN_INPUT_RE 的任何模式（DROP/DELETE/TRUNCATE 等纯 SQL 关键字）。留给 L2 SQL 护栏或 Agent 自己拒绝。

第二个（多语句注入）：拦。

;\s*(?:DROP|DELETE|INSERT|UPDATE|ALTER|TRUNCATE) 匹配分号后紧跟 DROP 的模式。

# guardrails.py
_SQL_WRITE_IN_INPUT_RE = re.compile(
    r";\s*(?:DROP|DELETE|INSERT|UPDATE|ALTER|TRUNCATE)\b"  # ← 命中
    # ...
)
面试要点："自然语言'帮我删掉'和 SQL 注入'DROP TABLE'是两回事。前者是用户的合理请求，后者是安全威胁。护栏不讨论意图，只匹配模式。"

五、多 Agent 编排 & Router 5 题

Q22 "你的 LangGraph 图拓扑是什么？节点之间怎么调度？"

图拓扑：

__start__ → router → (条件边) → sql / strategy / hbase / hive / data_quality
                                         │
                                         ├→ analysis → END
                                         └→ END (无 analysis 的 plan)

调度核心（_next_step + edge_router）：

def _next_step(state, results, current):
    plan = state["plan"]           # Router 输出的路线图
    executed = set(results.keys()) # 已打卡的 Agent
    pending = [s for s in plan if s["agent"] not in executed]  # 还没执行的

    if pending:
        return {"results": results, "next": pending[0]["agent"]}  # 去下一个
    if "analysis" in plan_agents and "analysis" not in executed:
        return {"results": results, "next": "analysis"}
    # plan 跑完 → 直接返回结果

def edge_router(state):
    return state.get("next") or "done"  # 读 next，LangGraph 查 targets 路由

比喻：plan 是路线图，executed 是已打卡的站，_next_step 对比两者决定下一站，next 是站牌，targets 是站牌→站点的翻译。

Q23 "Router 的硬规则和 LLM 怎么分工？为什么不全用 LLM？"

分工：硬规则优先，兜底 LLM。 route_override() 能确定的场景不调 LLM——零 token 成本。

场景路由方式原因
"你好""谢谢" 等闲聊硬规则 → plan=[]不需要数据查询，LLM 可能误判
"HBase scan orders"硬规则 → hbase关键字明确，100% 确定
"Hive 建表语句"硬规则 → hive同上
"提成比例是多少"硬规则 → strategy制度类，不需要查 SQL
"对比华东华南销售趋势"硬规则 → sql+analysis对比+数据标记=确定性路由
模糊/多意图LLM 兜底硬规则覆盖不了，交给模型判断

为什么不全部硬规则：自然语言无限变化。硬规则覆盖 80% 高频 case，剩下的交给 LLM。

为什么不全用 LLM：每次路由 ~250 token。高频闲聊全走 LLM 是浪费。LRU 缓存进一步省——同样 query 第二次直接命中缓存。

Q24 "RouterCache 怎么做的？什么策略？命中率多少？"

实现（cache.py）：

  • 策略：去标点、去空格、小写后精确匹配（不做模糊——安全第一）
  • 淘汰：LRU（max_size=100），超过淘汰最久未使用的
  • 统计：hits/misses 自动累计，hit_rate 属性返回 "15/20 (75%)"
def normalize(self, query: str) -> str:
    q = re.sub(r'[^\w\s]', '', query.lower())  # 去标点
    return ' '.join(q.split())                  # 去多余空格

# 查缓存
cached_plan = router_cache.get(state["query"])
if cached_plan is not None:
    plan_data = {"plan": cached_plan}
    span.task = f"缓存命中 ({router_cache.hit_rate})"

不缓存什么：硬规则命中的不写缓存（避免污染），只有 LLM 路径才写。

Q25 "为什么 Anthropic client 不能放进 LangGraph state？你怎么解决的？"

问题：Anthropic SDK 的 client 对象不能 JSON 序列化。如果放进 state，Checkpointer 写盘时会崩：TypeError: Type is not msgpack serializable。

解决方案：configurable 通道。

# langgraph 专门留给"不可序列化对象"的通道
config = {
    "configurable": {
        "thread_id": "default-session",
        "_client": client,        # ← 不可序列化对象放这里
        "_model": "deepseek-chat",
        "_trace": trace,
        "_router_cache": router_cache,
    }
}

# 节点函数从 config 取，不存 state
async def node_sql(state, config):
    client = config["configurable"]["_client"]   # ← 从 configurable 取
    model = config["configurable"].get("_model")

configurable 的特点：随每次调用注入节点，但不被 Checkpointer 持久化。专为运行时对象设计。

Q27 "TraceContext 是怎么工作的？为什么用 JSONL？"

TraceContext 概念（借鉴 OpenTelemetry）：

  • Trace：一次完整查询 = 用户输入 → 最终回答
  • Span：Trace 里的一个操作单元 = 一个节点（router/sql/analysis）

每个 Span 记录：node（哪个节点）、task（做了什么）、elapsed（耗时）、input_tokens、output_tokens、turns（多少轮 tool 调用）、error（是否超时）

为什么用 JSONL：

  1. append-only：每次 save 追加一行，不需要锁
  2. 按天分文件：logs/traces/2026-07-24.jsonl
  3. CLI 查看：python -m utils.tracer --today / --last 3
  4. 无需数据库：不会被连接管理、ORM 拖累
# 使用方式
trace = TraceContext(query="查华东销售额")
span = trace.start_span("router", "分析意图")
# ... 节点执行 ...
trace.finish_span(span, usage={"input_tokens": 100, "output_tokens": 50})
trace.save()  # 追加到今天的 JSONL

Q29 "eval_runner 怎么做的？LLM-as-Judge 怎么打分？"

两种模式：

  • --fast：只跑 guardrail 用例（6 条，零 LLM）——验证护栏拦截是否正常
  • --full：跑全类别（36 条）——覆盖 SQL 查询、制度检索、HBase/Hive 语法、对比分析等
  • --judge：LLM-as-Judge 打分——用一个独立的 LLM 调用评判回答质量

Eval 用例结构（eval_cases.py）：

{
    "id": "sql-001",
    "category": "sql",
    "query": "销售部有多少员工？",
    "expected_keywords": ["员工", "销售"],  # 回答必须含这些词
    "forbidden_keywords": ["无法", "抱歉"],  # 回答不能含这些词
}

--judge 模式：把 Agent 的回答 + 预期标准发给另一个 LLM，让它打分（1-5）并给出理由。用于回归检测——新改动是否降低了回答质量。

Q31 "你代码里到处都有 _ 前缀的变量（_client, _model, _inject_dq），什么意思？"

约定：_ 前缀 = "不应被 LangGraph Checkpointer 持久化"。

  • _client：Anthropic SDK 对象，不可序列化
  • _model：模型名字符串
  • _inject_dq：是否注入 DataQuality（首轮 True，后续 False）
  • _recalled_memories：pre-turn 向量召回结果（每轮重新算，不需持久化）
  • _conversation_summary：每次都重新构建，不需持久化
  • _stats：运行时累计统计
  • _trace：TraceContext 对象

本质上 _client 和 _model 已经废弃——现在走 configurable 通道（Q25）。但它们还在 TypedDict 定义里声明着以保持兼容。

七、Prompt 工程 & 成本优化 4 题

Q32 "cache_control 是怎么用的？省了多少成本？"

原理：

每轮 agent loop 都重复发送同样的 System Prompt + Tool Defs。Anthropic 的 prompt caching 让这些重复内容只按 cache hit 计费：

  • Cache miss：$3/M tokens（正常价格）
  • Cache hit：~$0.014/M tokens
  • 节省：~99.5% 的 system prompt 成本

实现（agent.py:58-75）：

def _build_cacheable_system(system_text: str) -> list[dict]:
    return [{
        "type": "text",
        "text": system_text,
        "cache_control": {"type": "ephemeral"},  # ← 5 分钟 TTL
    }]

# 调用时
cached_system = _build_cacheable_system(full_system_prompt)
response = client.messages.create(
    system=cached_system,  # ← 注意：传 list[dict] 而非 str
    messages=messages, tools=tools, ...
)

限制：必须标记至少 1024 tokens 才能触发缓存。System Prompt + Tool Defs 通常 1500-2500 tokens，刚好符合。ephemeral 类型 TTL 5 分钟，适合交互式对话场景。

面试要点："这是 Anthropic SDK 原生特性，一行 cache_control 标记就行。DeepSeek 兼容端点不一定支持，但代码结构不受影响——不支持就是正常计费而已。"
Q33 "你的 system prompt 是怎么生成的？为什么要用工厂函数而不是 MD 文件？"

用 Python 工厂函数 build_system_prompt()，不是静态 MD 文件：

def build_system_prompt(db_type="sqlite", user_role="数据分析师", extra_context=""):
    prompt = f"""你是 {db_type} 数据库分析 Agent。
    当前角色: {user_role}
    可用工具: list_tables, describe_table, run_query, ..."""

    if extra_context:
        prompt += f"\n\n[上下文]\n{extra_context}"  # ← 记忆注入点
    return prompt

为什么用工厂函数：

  1. 动态注入：db_type、user_role、向量记忆、权限声明——每个请求不同，MD 做不到
  2. 多 Agent 复用：LangGraph 的每个 Agent 有自己的 system prompt（在 agents.py 中定义），但都走同一个工厂模式
  3. 测试友好：传不同参数就能模拟不同场景，不需要读写文件

这是 learn-claude-code s05 Skill Loading 的等价实现——不是把知识全塞 system prompt，而是按需注入。

Q34 "LangGraph Checkpointer 存什么？为什么用 AsyncSqliteSaver？"

Checkpointer 存什么：

图每执行完一个节点，自动把完整 state（query、messages、plan、results、final_answer 等）序列化到 SQLite。同一 thread_id 的后续调用从这个文件恢复——messages 累积、results 保留。

为什么用 AsyncSqliteSaver：

  • Graph.ainvoke 走 async checkpoint API——同步版不兼容
  • 开发用 SQLite（零配置）；生产可换 PostgresSaver
  • 必须用 await MultiAgentRunner.create() 工厂方法——AsyncSqliteSaver 需要 await 初始化连接和建表，__init__ 是同步的做不到
# 状态持久化流程
runner.run(query, thread_id="session-123")
  → graph.ainvoke(state, config)  # 执行节点
  → Checkpointer 自动存 state 到 db/agent_state.db
  → runner.run(query2, thread_id="session-123")  # 同一会话
  → Checkpointer 恢复上次 state（messages 完整历史）

存什么，不存什么：messages（对话历史）存，plan/results/final_answer 存，_ 前缀字段（_client/_model/_trace）不存。

Q35 "你项目里有哪些设计上的 trade-off？面试官最爱问这个。"

至少能讲 5 个 trade-off：

Trade-off选择为什么
LangGraph orchestrator vs 去中心化邮箱当前用 LangGraph流水线任务（Router→SQL→Analysis）拓扑清晰。探索式协作更适合邮箱。harness 改造计划就是加 team 模式做对比。
Token 估算 vs API 精确计数本地估算为主在发请求前就要知道会不会超——不能等 API 报错。精确版 token_count_exact 作为补充，失败降级到估算。
纯规则护栏 vs LLM 护栏纯规则零延迟、零 token、确定性。误拦可以调正则，漏拦比误拦更危险。
SQL 改写 vs 数据库 RLSSQL 改写（演示层）生产环境应该用数据库原生 RLS Policy。正则改写只处理简单情况，复杂 SQL（子查询、JOIN、CTE）会失效。
Streaming vs 非 streaming两个版本都保留交互走 streaming（用户体验），测试走非 streaming（不需要看输出）。
ChromaDB vs Pinecone/WeaviateChromaDB 本地零配置、零成本、本地持久化。开发阶段不需要分布式向量库。生产换 Pinecone 只需改 VectorMemory 的 client 初始化。
面试要点：说 trade-off 的关键是给出"为什么这么选"——不是"我只会这个"，而是"在当前约束下这是最优解"。
